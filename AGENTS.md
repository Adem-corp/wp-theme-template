# AGENTS.md

Инструкции для AI-агентов (Claude Code, Cursor, Codex и т.д.), работающих с этим репозиторием.
Это стартовая классическая WordPress-тема **без Gutenberg**. Контент управляется через ACF + ACF Extended (ACFE).
Группы полей проектных блоков и дизайн Figma появляются при настройке конкретного сайта; нейтральный блок `example`
оставлен как образец и не регистрирует поля автоматически.

## Порядок работы над блоком

1. Если предоставлен дизайн Figma, изучить переданный фрейм (см. раздел «Работа с Figma»).
2. Найти и прочитать файл группы полей блока в `acfe-php/`. Если задача включает создание группы, сохранить её через
   PHP API ACF и дождаться генерации файла ACFE (см. раздел «ACF: поля»).
3. Написать `layouts/blocks/{block_name}/template.php`, используя только поля из файла группы.
4. Написать SCSS блока и, при необходимости, JS (Alpine.js / Carousel / Swiper / Fancybox).
5. После изменения PHP запустить PHPCBF для затронутых файлов, проверить их через PHPCS по WordPress Coding Standards
   (WPCS) и исправить оставшиеся ошибки. Конфигурация `phpcs.xml.dist` проверяет код темы.
6. После изменения SCSS проверить затронутые файлы через Stylelint с конфигурацией `.stylelintrc.json` и исправить ошибки.
7. После изменения SCSS или JS запустить `npm run build` и проверить собранные файлы.

Итогового отчёта не нужно: достаточно короткого сообщения о том, что сделано. Если обязательную проверку запустить
не удалось, указать это в сообщении.

## CLI в LocalWP

Перед запуском PHP CLI, WP-CLI или MySQL для этого сайта загрузить переменные окружения LocalWP из
`app/.envrc` **в той же оболочке**, где выполняется команда. Из корня темы:

```bash
source ../../../../.envrc
php -r 'require "../../../wp-load.php"; echo get_bloginfo( "name" ), PHP_EOL;'
```

Файл `.envrc` задаёт путь к PHP LocalWP, `PHPRC`, `MYSQL_HOME` и настройки WP-CLI. Системный `php` без этих переменных
может не подключиться к MySQL, даже когда сайт работает. Если MySQL socket недоступен из песочницы, повторить команду
с разрешённым доступом к окружению LocalWP; только после этого считать БД недоступной. Не фиксировать в инструкциях
пользовательские пути из `.envrc` — LocalWP создаёт их для конкретной установки.

## Стек и общие ограничения

- WordPress: кастомная классическая тема, без блоков и паттернов Gutenberg.
- PHP: ACF + ACF Extended (ACFE).
- JS: Alpine.js для интерактива во всей теме; Carousel, Swiper и Fancybox подключаются при необходимости проекта.
- CSS: SCSS, БЕМ и собственная конфигурация `.stylelintrc.json`.
- SCSS и JS собираются существующим Gulp (`gulpfile.js`, `npm run build`); готовые файлы подключаются через
  `wp_enqueue_scripts` в `inc/theme/assets.php`. Не добавлять webpack, Vite или другой параллельный сборщик.

## Работа с Figma

- Если дизайн конкретного блока предоставлен в Figma, перед вёрсткой агент должен изучить его, а не додумывать
	разметку/отступы/цвета самостоятельно. Нейтральный стартовый пример не связан с Figma.
- Для доступа к дизайну использовать Figma MCP-коннектор (если подключён): получать через него структуру блока,
	скриншот, значения переменных (цвета, шрифты, отступы) и метаданные слоёв конкретного фрейма/ссылки, которую передал
	разработчик.
- Работать только с тем фреймом, ссылку на который передал разработчик. Не загружать целую страницу или весь файл.
- Значения цветов и шрифтов, полученные из Figma-переменных, сопоставлять с уже существующими переменными в
	`_variables.scss` (см. раздел «Переменные»), а не заводить новые дублирующие значения.
- Если задача требует соответствия конкретному макету, но ссылка на фрейм/страницу Figma не передана — уточнить её у
	разработчика, а не искать нужный блок в файле самостоятельно.
- Значения из дизайна (отступы, размеры, шрифты) не переносить один в один "как есть" — округлять до аккуратных чисел
	(например, до чётных или кратных 4/8), так как в самом дизайне значения могут быть неточными.

## ACF: поля

**При создании или изменении групп полей использовать внутренний PHP API ACF с сохранением в БД.** ACFE автоматически
генерирует PHP-файлы групп в `acfe-php/`. Если задача касается только вёрстки, использовать существующую группу без
изменения её полей.

В стартовой теме `acfe-php/` пуст: группы блоков появляются после установки WordPress и ACF/ACFE для конкретного сайта.
Шаблон `layouts/blocks/example/template.php` иллюстрирует поле `heading`, но не означает, что группа уже создана.
Локальная группа настроек форм в `inc/forms/registration.php` — часть базовой темы и исключение из описанного ниже
порядка сохранения проектных групп блоков.

### Сохранение и синхронизация

- Выполнять операции в загруженном окружении WordPress (`wp-load.php`) через PHP CLI или WP-CLI, без браузера и админки.
	Перед запуском загрузить `app/.envrc` в той же оболочке, как описано в разделе «CLI в LocalWP» выше.
- Новую группу с вложенными полями сохранять через `acf_import_field_group()`. Для изменений использовать PHP API ACF
	(`acf_update_field()`, `acf_update_field_group()`), сохраняя существующие ключи, поля и настройки.
- Перед изменением существующей группы найти её **числовой ID в БД** по `post_type = acf-field-group` и `post_name = key`;
	убедиться, что совпадение ровно одно. `acf_get_field_group( $key )` может вернуть группу из PHP-экспорта с `ID = 0`:
	передача такой группы в `acf_import_field_group()` создаёт дубль с тем же ключом. При нескольких совпадениях сначала
	разобраться с дублями, не импортировать группу повторно.
- Для Flexible Content с clone-полями брать **неразвёрнутую структуру** из исходного PHP-экспорта ACFE, добавлять
	layout и сохранять через `acf_import_field_group()` с установленным числовым `ID` существующей группы. Не брать
	`acf_get_fields()` для повторного сохранения и не передавать в `acf_update_field()` значение, полученное из
	`acf_get_raw_field()` без проверки: при загрузке WordPress clone-поля могут развернуться и заменить исходные ключи
	в экспорте. После сохранения проверить diff: прежние layout и clone-поля должны остаться без изменений.
- Включать PHP-синхронизацию группы: `'acfe' => array( 'autosync' => array( 'php' ) )`. После изменения полей сохранять
	также их группу, чтобы ACFE обработал событие `acf/update_field_group` и сам создал или обновил файл в `acfe-php/`.
- Не ограничиваться `acf_add_local_field_group()`: эта функция регистрирует группу только в PHP и не сохраняет её в БД.
	Не заменять API прямыми SQL-запросами на запись или ручной генерацией PHP-файлов.
- При добавлении layout в `blocks` сохранять clone-поле и настройки Flexible Content через API, затем сохранять группу
	«Контент». Существующие layout'ы и контент страниц должны сохраняться без изменений.
- При сохранении группы временно отключать фильтр `acfe/flexible/thumbnail`, чтобы вычисленный URL не попал в БД и
	PHP-экспорт; затем восстанавливать фильтр.
- После операции проверять оба результата: группу и поля в БД (без подмены локальной PHP-регистрацией) и автоматически
	сгенерированный файл ACFE. Также проверить, что по ключу группы в БД осталась ровно одна запись. Проверять diff и
	PHP-синтаксис; при недоступной БД не подменять результат созданием файла.

### Использование полей в шаблонах

- Источник правды о полях — сгенерированный файл группы `block:{block_name}` в `acfe-php/`. Найти его (например, через
	`git status` / `git diff` или поиск по `'title' => 'block:{block_name}'`) и взять оттуда имена полей, типы,
	вложенные поля и форматы возврата.
- Имена полей в `template.php` должны **точно** совпадать с именами в этом файле. Не придумывать, не переименовывать и
	не добавлять поля.
- Если блок использует `clone` другой группы (например, `title`), при необходимости прочитать и её файл.
- При создании и регистрации нового блока можно читать файлы существующих блоков в `layouts/blocks/` и их группы
	в `acfe-php/`, чтобы сохранить общую структуру и стиль темы. Имена, типы и настройки полей нового блока брать
	из его собственной группы; не копировать поля других блоков без необходимости.
- Если файл группы не найден или структура полей неясна, а создание группы не входит в задачу — уточнить у разработчика.
- Не открывать админку WordPress / интерфейс ACF, не использовать браузер или скриншоты для работы с полями.
- Не создавать и не редактировать файлы в `acfe-php/` вручную: их генерирует ACFE при сохранении групп через API.
- Каждый layout во Flexible Content `blocks` ссылается на отдельную группу полей через `clone` с
	`display => 'seamless'`, без префиксов имени и подписи.
- У любого clone-поля, включая клон общей группы заголовка `title` внутри `block:*`, оставлять собственные `name` и
	`label` пустыми: отображаемые имена и подписи приходят из клонируемых полей. Сохранять уникальный технический `key`
	clone-поля; у существующего поля не менять его, чтобы не потерять связь с сохранёнными значениями.

### Вывод значений

- Для полей, в которых выбираются записи CPT (`Relationship`, возврат `Post Object`), выводить записи через `foreach` с
	`setup_postdata( $post )` внутри цикла и `wp_reset_postdata()` после него.
- Изображения приходят как `id`: выводить через `adem_dynamic_thumbnail()` или `wp_get_attachment_image( $id, 'full' )`
	(см. раздел «PHP: общие правила»).

## Структура блоков

- Каждый блок — отдельная папка: `layouts/blocks/{block_name}/template.php`
- Каждый блок — это `<section>` с классами по БЕМ (`block-name`, `block-name__element`, `block-name--modifier`)
- Блоки подключаются автоматически через `layouts/partials/blocks.php`
- Blocks — это поле Flexible Content с именем `blocks`, в группе полей **«Контент»**
- Файл `preview.jpg` (575×250) в папке блока агент не создаёт — его добавляет разработчик.
- Thumbnail layout'а в группе «Контент» не заполнять: фильтр `acfe/flexible/thumbnail` в `inc/integrations/acf.php`
	сам подставляет `layouts/blocks/{block_name}/preview.jpg`, если файл существует. В сохранённых настройках layout'а
	оставлять `acfe_flexible_thumbnail => false`.
- Не использовать `<ul>` для формирования разметки блоков: `<ul>` допустим только для текстовых списков. Карточки и
	другие повторяющиеся элементы размещать в обычном контейнере `<div>`.
- Составные имена блоков и обычных ACF-полей писать через дефис: `order-steps`, `block:order-steps`, `step-text`.
	Один slug использовать для имени layout и папки блока; существующие внутренние ключи ACF при переименовании сохранять.

### Название группы полей блока

- Группа полей, соответствующая layout'у блока, называется по шаблону `block:{block_name}`, например `block:hero`.
- Такая группа полей в админке должна быть **неактивна** (Active — выключено): она подключается только как clone-поле
	внутри layout'а, а не отображается отдельно.
- Создание группы само по себе не означает добавление layout в `blocks`.

### Контейнер

- Внутри каждого блока, а также внутри `header` и `footer`, для ограничения ширины контента использовать готовый класс
	`.container` — стили для него уже предусмотрены.
- Не создавать собственный контейнер/обёртку с аналогичной задачей.

### Партиал заголовка

- После создания группы `title` общие ACF-поля заголовка хранятся в ней. В hero и последующих проектных блоках подключать её
	через поле `clone` с `display => 'seamless'`, без собственных `name` и `label` и без префиксов имени и подписи. Группа содержит поле
	`title` с вложенными `text` и `type`; не создавать их заново внутри блоков.

Использовать `layouts/partials/title.php` через:

```php
get_template_part(
	'layouts/partials/title',
	null,
	array(
		'title' => $block_title,
		'class' => 'block-name__title',
	)
);
```

Сигнатура `title.php`:

- `$args['title']` — массив с полями:
	- `'text'` (string)
	- `'type'` (`h1` / `h2` / `h3`)
- `$args['class']` — дополнительный CSS-класс

## PHP: общие правила

- Соблюдать **WordPress Coding Standards (WPCS)**. После каждого изменения PHP запускать PHPCBF для всех затронутых
	файлов, затем проверять их через PHPCS. Оставшиеся нарушения исправлять вручную и повторять PHPCS до успешной
	проверки.
- Для вывода nonce-полей в формах использовать `adem_wp_nonce_field()`, а не `wp_nonce_field()`:
	хелпер убирает `id` у nonce-поля, чтобы несколько форм на странице не создавали одинаковые ID.
- Если внутри `if`, `foreach`, `while` и подобных конструкций нет HTML-разметки, использовать фигурные скобки `{}`.
	Альтернативный синтаксис (`endif;`, `endforeach;` и т.д.) оставлять только для участков шаблона с HTML внутри
	конструкции.
- Открывающий PHP-тег и управляющую конструкцию перед HTML писать в одну строку для `if`, `foreach`, `while` и других
	конструкций с альтернативным синтаксисом: `<?php if ( $description ) : ?>`, `<?php foreach ( $items as $item ) : ?>`.
	Если условие или источник цикла слишком длинные, подготовить их в переменной до HTML. Закрывающие теги
	`<?php endif; ?>`, `<?php endforeach; ?>`, `<?php endwhile; ?>` и аналогичные ставить на отдельных строках после HTML.
- Все ACF-поля, используемые в шаблоне, выносить в переменные **в начале файла**, а не вызывать `get_field()` /
	`get_sub_field()` посреди разметки.
- Изображения из ACF возвращаются в формате `id` (не array, не url).
	- Для обычного вывода: `adem_dynamic_thumbnail( $id, $width, $height, $crop, $attr )`
	- Для полного размера: `wp_get_attachment_image( $id, 'full' )`
- При выводе HTML из `adem_dynamic_thumbnail()` всегда оборачивать вызов в `wp_kses_post()`.
- Не проверять ID перед отдельным вызовом `wp_get_attachment_image()`: при пустом ID функция возвращает пустую строку.
	Условие сохранять, если от наличия изображения зависит вывод окружающего контейнера или структура блока.
- Для повторяющихся элементов разметки использовать `get_template_part()`:
	- карточки → `layouts/cards/`
	- партиалы → `layouts/partials/`
- Файлы карточек в `layouts/cards/` называть по шаблону `name-card.php`, где `name` — короткое слово,
	характеризующее карточку (например, `service-card.php`).
- Если к массиву элемента нужно добавить аргументы для `get_template_part()` (например, CSS-класс карточки), передавать
	результат `array_merge()` непосредственно в вызов. Не изменять исходный массив элемента перед вызовом.
- Не использовать `nl2br()` и `white-space: pre-line` для переносов строк из ACF-полей.
- Не использовать `wpautop()` для вывода ACF-текста: пользователь добавляет нужные HTML-теги вручную, выводить
	разрешённую разметку через `wp_kses_post()`.

### Массивы

Пример передачи дополнительного класса карточке:

```php
get_template_part(
	'layouts/cards/adv-card',
	null,
	array_merge(
		$card,
		array(
			'class' => 'why__card',
		)
	)
);
```

- Если в вызове функции среди аргументов есть непустой массив, оформлять вызов многострочно: каждый аргумент на
	отдельной строке, закрывающая скобка — на отдельной строке. Пустой массив `array()` или `[]` сам по себе не требует
	переноса;
	объявления функций это правило не затрагивает.
- PHP-массивы с несколькими элементами (например, аргументы для `get_template_part()`) писать не в одну строку, а каждый
	элемент — на отдельной строке, с закрывающей скобкой на новой строке:

```php
array(
	'items' => $footer_socials,
	'class' => 'footer__social',
)
```

### Атрибуты HTML-тегов

- В шаблонах не использовать тег `<p>`, если пользователь явно не попросил его; для обычного текстового блока
	использовать `<div>`.
- Если атрибуты открывающего тега не помещаются в 120 символов — переносить их на новую строку, но **не по одному
	атрибуту на строку**: первый атрибут остаётся на строке с тегом, остальные обычные атрибуты переносятся одним блоком
	на следующую строку (через пробел, как обычно).
- Закрывающий `>` открывающего тега **всегда** оставлять на строке с последним атрибутом, в том числе если последний
	атрибут относится к Alpine.js (`@click`, `x-show`, `x-cloak`, `x-transition` и т.д.). Не писать `>` отдельной строкой.
- Атрибуты, относящиеся к Alpine.js (`x-data`, `x-show`, `x-on:...` / `@...`, `x-bind:...` / `:...`, `x-transition` и
	т.д.), писать **каждый на отдельной строке**, и располагать их **после** обычных атрибутов.

Пример (обычные атрибуты):

```php
<img src="<?php echo esc_url( get_template_directory_uri() . '/assets/images/logo.svg' ); ?>" width="226" height="50"
		alt="Светлана">
```

Пример (обычные атрибуты + Alpine.js):

```php
<div class="block-name__panel" id="panel"
	x-data="{ open: false }"
	x-show="open"
	@click.outside="open = false">
```

## CSS

- Методология БЕМ для классов блоков и компонентов. Существующие служебные классы (`.container`, `.hidden`,
	`.clearfix`, `.reset-list`) остаются исключением.
- В названиях классов для изображений использовать `img`, а не `image` (например, `block-name__img`); для кнопок —
	`btn`, а не `button` (например, `block-name__btn`).
- `.editorconfig`: табуляция, `indent_size = 2`.
- `line-height` всегда указывать относительным числом без единиц (например, `1.4`), не в процентах и не в пикселях.
- Если одновременно заданы вертикальные и горизонтальные отступы, использовать общее правило `padding` или `margin`
	(например, `padding: 20px 40px`), а не сочетание `padding-block` с `padding-inline` или `margin-block` с `margin-inline`.
	Если задана только одна ось, использовать `padding-block`, `padding-inline`, `margin-block` или `margin-inline`.
	Для отдельных сторон использовать обычные свойства `margin-top`,
	`padding-right` и т.п.; не заменять их на `*-block-start`, `*-inline-end` и аналоги. Общий сброс всех отступов
	(`margin: 0`, `padding: 0`) можно оставлять сокращённым.
- Для блоков с необязательной соседней колонкой (например, текст и цитата) использовать flex: основной контент
	должен автоматически занимать свободную ширину, если соседнего элемента нет. Не добавлять условный класс только
	для переключения количества колонок.

### Вложенность селекторов

- Модификаторы (`&--...`) располагать сразу после собственных стилей класса, к которому они относятся, включая его
	`@include`-миксины, и перед вложенными элементами. Например, модификатор блока `&--vip` должен находиться в начале
	блока после его основных стилей, а не в конце после всех `&__...`.
- Не объединять модификатор блока и его элемент в конструкции вида `&--3 &__card`.
- Внутри модификатора блока писать отдельный вложенный селектор с полным классом элемента.

Неправильно:

```scss
.simple-cards {
	&--3 &__card {
		flex-basis: calc((100% - 48px) / 3);
	}
}
```

Правильно:

```scss
.simple-cards {
	&--3 {

		.simple-cards__card {
			flex-basis: calc((100% - 48px) / 3);
		}
	}
}
```

### Списки

- Если у `<ul>` нужно сбросить `margin`, `padding` и `list-style` — по возможности вешать готовый класс `.reset-list`, а
	не прописывать сброс вручную в стилях блока.
- В повторяющихся шагах и карточках с последовательными номерами использовать `counter-reset` на контейнере,
	`counter-increment` на элементе и `counter()` в `::before`. Не добавлять в шаблон отдельный элемент для номера и не
	вычислять порядковый номер в PHP.

### Кнопки

- Общие стили кнопок хранить в отдельном файле — `components/_buttons.scss`.
- Кнопка — самостоятельный компонент: базовые стили (вид, паддинги, цвета, hover через `@include hover`) описываются в
	`_buttons.scss`, а не дублируются внутри стилей блока.
- Позиционирование кнопки относительно родителя (например, отступы, выравнивание внутри блока) прописывается в
	классе-контейнере блока (`block-name__btn`), а не в самом классе кнопки.

### Меню

- Стили всех меню хранить в одном файле — `components/_menus.scss`.
- Класс каждого меню начинается с `menu-`, далее указывается его расположение: `menu-main`, `menu-burger`, `menu-footer`
	и т.д.
- Меню — это самостоятельный компонент: его собственные стили (`.menu-main`, `.menu-burger` и т.д. в `_menus.scss`) не
	должны включать позиционирование этого меню относительно родителя (`position`, `grid-column`, `margin` для размещения
	и т.п.).
- Стили, отвечающие за расположение конкретного меню внутри блока (например, меню внутри `header`), прописываются в
	классе-контейнере этого блока (`header__menu`), а не в классе самого меню.

### Переменные

- Шрифты задавать через CSS custom properties `--font-...` из `_variables.scss`.
- Цвета брать точно из макета. Если значение совпадает с существующей переменной `--color-...`, использовать её;
	если подходящей переменной нет — указывать точное значение цвета из макета напрямую.
- Не использовать `color-mix()` и не подбирать приближённые цвета смешиванием: указывать цвет, заданный в дизайне.

### Hover

- Для псевдокласса `:hover` использовать миксин `@include hover`, а не писать `&:hover` напрямую.

```scss
&__btn {
	@include hover {
		background: var(--color-accent);
	}
}
```

### Медиазапросы

- Для медиазапросов использовать существующие миксины (`@include laptop(...)`, `@include mob(...)` и т.п.).
- Миксин обязательно должен быть **внутри конкретного селектора**, вокруг тех свойств, которые меняются, а не
	оборачивать сразу несколько селекторов одним блоком `@include`.
- Между обычными свойствами и `@include` (и между несколькими `@include` подряд) пустых строк не оставлять — писать без
	отступов, единым блоком.

Неправильно:

```scss
@include to(1200px) {
	&__logo {
		flex-basis: 160px;
	}

	&__menu {
		gap: 12px;
	}
}
```

Также неправильно (пустые строки между свойствами и миксинами):

```scss
&__panel {
	display: flex;
	gap: 20px;

	@include to(1200px) {
		gap: 16px;
	}

	@include tablet {
		display: none;
	}
}
```

Правильно:

```scss
&__logo {
	@include to(1200px) {
		flex-basis: 160px;
	}
}

&__menu {
	@include to(1200px) {
		gap: 12px;
	}

	a {
		@include to(1200px) {
			font-size: 11px;
		}
	}
}

&__panel {
	display: flex;
	gap: 20px;
	@include to(1200px) {
		gap: 16px;
	}
	@include tablet {
		display: none;
	}
}
```

## JS

- Alpine.js — основной способ реализации интерфейсного интерактива во всей теме: в шапке, футере, проектных блоках,
	меню, табах, аккордеонах, тоглах и дропдаунах. Не ограничивать его только новыми блоками и не добавлять для таких
	элементов отдельные vanilla JS-обработчики.
- Скрипт Alpine копируется из установленного npm-пакета в `assets/vendor/alpinejs/` командой `npm run build` и
	подключается на всех страницах через `inc/theme/assets.php`. Существующий `assets/js/main.js` пока содержит
	отправку форм и телефонную маску на vanilla JS; при изменении этого интерактива переводить его на Alpine.js.
- Для слайдеров/каруселей использовать Carousel или Swiper после выбора и подключения библиотеки в проекте.
- Fancybox (@fancyapps/ui) — для попапов и лайтбоксов после подключения библиотеки в проекте.
- Для Fancybox-ссылок на элемент страницы (`href="#id"`) не задавать явно тип `inline`: достаточно атрибута
	`data-fancybox`.

## Иконки

- Все статичные иконки хранить в общем SVG-спрайте: `/assets/images/sprite.svg`.
- URL спрайта получать через `adem_svg_sprite_url( 'i-car' )`: хелпер сам добавляет ID символа.
	Не собирать URL вручную через `get_template_directory_uri()`.
- В коде вставлять иконку через `<svg>` + `<use>`, а не инлайнить SVG-разметку напрямую и не подключать иконку как
	`<img>`:

```php
<svg width="21" height="18">
	<use xlink:href="<?php echo esc_url( adem_svg_sprite_url( 'i-car' ) ); ?>"></use>
</svg>
```

- `width`/`height` у `<svg>` указывать под конкретный кейс использования (реальные размеры иконки в макете).
- `id` символа в спрайте — с префиксом `i-` (`i-burger`, `i-phone`, `i-arrow` и т.д.).
- По возможности преобразовывать обводки иконок в один залитый `<path>` внутри `<symbol>`: задавать
	`fill="currentColor"`, не оставлять `stroke` и связанные с ним атрибуты. Если такое преобразование заметно искажает
	иконку, сохранять необходимые атрибуты.
- Удалять из спрайта лишние метаданные и атрибуты, упрощать координаты и команды `d`, но сохранять читаемые отступы,
	разделение символов и переносы длинных путей. Не превращать весь файл в одну минифицированную строку.
